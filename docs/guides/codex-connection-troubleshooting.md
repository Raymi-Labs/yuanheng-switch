# Codex 上游连接失败排查

如果错误中出现 `YuanHeng Switch local proxy failed`、`/responses` 和 `上游连接失败`，说明本地代理接到了请求，但出站连接未完成。上下文压缩也经过这条链路，会受到同一网络故障影响。该消息本身不能证明账号失效、额度不足或模型不可用。

从 v0.1.74 开始，错误提供 `network=...` 分类；可以同时保留 `io` 和 `os` 编号帮助排查，不包含请求正文、原始 URL 或凭据。

| 分类 | 检查方向 |
|---|---|
| `dns` | DNS 解析是否正常，目标域名是否落到了预期代理规则 |
| `connection_refused` | 本机出站代理是否开启、端口是否正确，或目标服务是否拒绝连接 |
| `proxy_tunnel` | 出站代理认证、节点及 CONNECT 隧道 |
| `tls` | 系统时间、证书信任、TLS 检查工具或代理节点；不要通过关闭证书验证解决 |
| `network_unreachable` | 网络连接和路由是否可达 |
| `connection_closed` | 连接途中被关闭，核对节点和网络稳定性 |
| `timeout` | 网络连接或等待上游响应超时；HTTP 状态仍为 504 |
| `unknown` | 底层库未提供可安全识别的原因，结合相同时刻的代理日志继续定位 |

这些分类来自错误源链，属于排查方向，不是对 DNS 污染、节点故障或服务端故障的自动定论。

## 本地端口返回空正文 503

`127.0.0.1:15721/v1/responses` 的 `503 Service Unavailable: Unknown error` 也可能来自本地服务暂时没有监听：系统 HTTP 代理可以把连接拒绝转换为空正文 503。需要对照桌面日志中的 Core 巡检记录、Core 的停止/启动时间及监听端口，不能直接认定上游限流或模型不可用。

Core 健康巡检使用绕过代理的本机管理接口。连续探测失败后，恢复流程先核验进程、端口和 macOS 注册服务；仍存活、监听或无法确认时保留服务，不自动终止。失败后以 5、10、20、40、60 秒间隔退避，成功后恢复正常巡检。日志保留 `stage`、`elapsed_ms`、HTTP 状态及安全的错误类别，不写入凭据或响应正文。

真正退出的 Core 仍可恢复；存活但持续无响应的 Core 需要在确认没有进行中的任务后通过现有重启入口处理。升级时同时核对桌面应用和 Core 的实际版本，避免启动项目构建目录中的旧应用副本；发布新安装包本身不会替换已运行的旧桌面进程。正常空闲升级沿用既有保护，不代表所有并发到达的请求都能严格零中断。

## 使用官方 Codex 账号与外部代理

官方账号请求使用 `chatgpt.com`。只有 `openai.com` 的规则无法覆盖该域名。外部代理若先按 DNS 结果命中 `GEOIP,CN,DIRECT`，可能把该请求误分流为直连，出现间歇性连接失败。

在 Shadowrocket 等工具中检查 `chatgpt.com` 的域名规则是否位于 GEOIP 直连规则之前，并指向自己选定的可用代理策略。例如 Shadowrocket 配置中的规则形式为：

```text
DOMAIN-SUFFIX,chatgpt.com,你的代理策略名称
```

替换成实际存在的策略名称；不要照搬其他用户的节点名称。核对代理日志的最终命中规则和 DNS 来源，必要时按所用工具支持的方式调整 DNS。客户端不会自动修改这些设置或替换 DNS 服务。

## 客户端更新的作用与边界

v0.1.74 在出站配置未变化时保留连接池，避免每秒重新握手；显式代理、环境代理或系统代理设置变化后更新客户端。配置更新失败保留原有可用客户端，已发出的请求继续使用原客户端完成。未填写全局出站代理时跟随系统代理，不代表强制直连。

这项优化惠及共享 HTTP 客户端的请求，但无法修复外部代理内的错误分流、节点断连或上游服务故障。Claude 原始头转发与图片独立客户端仍遵循各自策略。没有新增失败请求的自动重放；请求超时后是否重试由调用方决定。

排查时优先保留故障时刻与错误分类，对照外部代理日志；恢复后的健康检查或无凭据 HTTP 探测只能说明当时可达，真实模型请求成功才说明对应推理链路恢复。

## 本机请求被系统代理接管

`Reconnecting …/5`、`stream disconnected before completion: error sending request` 或访问 `127.0.0.1:15721` 的 503，不足以判断是哪一段失败。链路为 **Codex → 本机 Core → 上游**。请求未到 Core 时，请对照同一时刻的 Codex 日志与本机探针；Core 请求日志没有记录不能独立证明代理故障。

智能体检新增三个独立项目：本机直连与当前客户端代理路径对照、Codex 实际进程绕过环境、Core 上游近期轻量检查。对照使用无凭据、无计费的 `/health`，禁止重定向并核验 Core 身份；只有直连成功且代理路径失败或返回非 Core 内容时，才提示代理可能影响本机连接。默认路径沿用元衡当前进程环境和系统代理，不能完全代替外部客户端自己的代理实现、PAC、VPN/TUN 或启动环境。Core 上游检查复用最近 15 分钟的选路证据；没有近期结果时到设置的连接线路中主动运行轻量检查。

| 证据 | 定位方向 |
|---|---|
| Core 未运行或直连失败 | 先查 Core 进程、监听端口；不直接判断代理绕过缺失 |
| 直连成功，当前客户端代理路径失败 | 检查本机绕过条目及 Codex 实际进程环境 |
| Core 接到请求，出站 `network=...` 失败 | Core 到上游的 DNS、代理、TCP/TLS 路径 |
| 上游返回 HTTP 错误 | 结合具体上游响应和权限信息；状态码不能独立归责 |
| 已开始流式输出但未完整结束 | 检查上游/客户端取消及连接中断；不能按网页 200 验收 |

### 启动保护与 macOS 登录兼容

元衡启动的 Codex CLI 与 App Server 合并 `NO_PROXY`、`no_proxy` 中原有条目，并加入 `localhost,127.0.0.1,::1`。macOS 桌面启动通过 LaunchServices `--env` 注入；已有实例不能继承新环境，未确认保护时提示保存任务后重启。受控重启仅终止当前用户所选应用包的主进程和模型后端，不强制杀死所有同名进程。启动后检查实际内核进程环境，不能读取时明确未确认。

智能体检展开后点击“检查兼容状态”，可显式启用当前用户的登录修复：

- 写入 `~/Library/LaunchAgents/com.yuanheng.loopback-proxy-bypass.plist`，登录脚本与恢复记录位于元衡配置目录的 `loopback-proxy-bypass/`。
- 为后续启动且支持这两个变量的 GUI 应用保护本机连接，涵盖 Dock/Finder。保留既有绕过条目及公网代理，不改第三方代理规则。登录脚本合并登录时的新条目，不自动重启应用。
- “重启 Codex 并复验”需要用户先保存任务并明确确认；模型后端尚未出现时仍需启动一次会话再检查。配置存在、环境生效、真实请求完成是不同状态。
- “撤销兼容修复”恢复本次登录应用前的环境并移除元衡自己的 LaunchAgent。外部修改冲突时保留配置并报错；不会接管或删除手工建立的 `local.codex.loopback-proxy-bypass.plist`。空值恢复为 unset，二者均表示无绕过条目。已有进程须再次重启。

登录修复只针对 macOS。其他平台的元衡 App Server 和普通可执行文件启动合并绕过；Windows Store/手动启动路径没有可验证的登录环境注入能力，不能据此宣称已覆盖。若客户端自行覆盖代理变量，仍需依据其实际日志判断。

### 验收

自动测试用本机模拟 HTTP 代理重现误转发，要求修复后本机请求不再进入代理，同时公网测试地址仍经代理。登录脚本隔离测试覆盖大小写、原条目、重新登录时新环境、重复执行、撤销冲突、部分写入失败回滚及 shell 特殊字符。macOS 可显式运行 `YUANHENG_NATIVE_PROXY_QA=1 cargo test --manifest-path src-tauri/Cargo.toml --lib native_launchservices_acceptance -- --ignored --test-threads=1`：使用临时合成应用验证 LaunchServices 注入、普通 GUI 启动、进程继承、退出及原环境恢复，不重启真实 Codex；若已有元衡兼容安装则拒绝该测试。

正式排障仍须保持 VPN 开启，用实际 Codex 和原有模型配置完成完整流式响应，并检查实际模型后端。合成 GUI、脚本模拟重新登录、网页 200 均不能替代目标机器真实 Dock 启动、重新登录与模型调用验收。
