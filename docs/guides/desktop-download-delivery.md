# 客户端下载分发与更新恢复

## 客户端

官方镜像与 GitHub 固定版本包各试下载最多 256 KiB，先完成的源用于本次更新；剩余探测随即取消。仅识别当前项目固定命名的三平台包，不根据任意主机名猜测备用地址，不向备用源传递额外认证头。代理继续采用现有用户设置、环境或系统代理。

连接 10 秒、响应或连续无数据 15 秒受限；连续 8 秒低于 128 KiB/s 且尚有备用源时切换。每源最多两次下载尝试，第二轮允许持续慢速但仍有数据的线路，整个操作最多 30 分钟，包上限 256 MiB。这里的连接限制不含试下载，试下载各自最多 6 秒。

切源/断流时在本次操作内通过 Range 续传，校验范围和总长度；服务器忽略 Range 返回 200 则从零重下。字节暂存在内存，不跨点击重试或程序重启持久化。完整包必须用原有 Tauri 公钥与该版本签名验证；签名失败丢弃字节再尝试另一源。Tauri 安装、退出清理和重启顺序保持不变，后端互斥防止重复安装。

小块择源不保证后续每秒都最快，也不代表国内三网/海外所有地区测速。速度改善需在实际用户网络独立验收。

## 源站缓存头

2026-10-12 检查发现版本包同时带 `public, max-age=31536000, immutable` 与 `no-store, no-cache...`。前者来自应用，后者来自源站 Nginx 通用代理 location。将 [下载专用 location](../../deploy/nginx/desktop-download-location.conf) 合并到实际 HTTPS server，可使下载包保留应用的缓存头，错误响应仍保留 `no-store`。该片段依赖现有 `nan_cluster` upstream，不是独立完整 Nginx 配置。

只读取 `/desktop/update/releases/` 的版本化公开文件；更新清单、上传接口、认证和 API 不迁移到此 location。先备份并记录现有配置 SHA-256，在副本合并后执行 `nginx -t -c <候选主配置>`；获准上线时再次核对旧配置摘要，替换后 `nginx -t`，再平滑 reload。失败恢复原文件；验证 200、206、HEAD、404、最新清单和正常 API，再保留备份。

上线后的成功响应应只有一套长期缓存策略，错误响应不能被长期缓存。验证实际公网响应，不能只验证 `localhost`。若入口中转层也添加禁止缓存头，需要在那里作相同范围的修复。

修复响应头不会自动产生 CDN 节点。本片段没有启用磁盘代理缓存，也不代表首次下载已经提速；面向国内与海外的下载 CDN/缓存中转仍应根据各地实测选择，在版本文件上传、签名及哈希校验通过后才发布更新清单。原域名路径可保留，旧客户端从服务器调整中受益。

缓存状态来自 `CF-Cache-Status`，重复请求不一定命中相同节点。Mac 命中 NRT，腾讯云请求先后落在 SEA/ATL/PDX，源站请求落在 YYZ/ATL；不能将“第二次请求”一律称为热缓存。Mac 的 curl 没有显式 HTTP 代理，但目标解析为 `198.18.*`，且系统 HTTP 代理已开启，仍属于现有代理/TUN 网络，不能作为中国大陆三网直连数据。

8 次 R2 整包下载均为 HTTP 200、完整字节数及 SHA-256 一致；四轮 `Range: bytes=100000-199999` 均为 HTTP 206、长度 100,000、总长正确，分段摘要也与原文件对应字节一致。成功包实际返回 `Cache-Control: max-age=14400`，已观测 MISS → HIT 和递增 Age；缺失文件为 404 / DYNAMIC。此次没有安装客户端，也没有创建新的 API 密钥或购买套餐。

此结果支持把 R2/CDN 作为正式下载源的候选，同时保留 GitHub；不证明 R2 在所有地区都比 GitHub 快。切换前仍需补齐国内直连、高峰期验证和所有平台安装包/签名的自动同步，并核对版本包长期缓存、清单不缓存及 404 策略。当前客户端只识别原官方镜像/GitHub 地址；直接将清单改成新主机会回到 Tauri 单源下载，必须先保留原路径的兼容跳转或明确扩展官方地址识别，验证切源和签名流程后再上线。不能修改全站 ServerAddress 来替代独立下载域名配置。
