# Agent Note: meta-api.com 首选线路与官网入口

Status: implemented

## Problem

官方新增 meta-api.com，客户端目前只有跳板与 CF 两条候选，官网链接也仍指向旧域名。用户要求三线可选、自动优先新域名及客户端进入官网使用新域名。

## Decision

复用 Core 选路器，新增 primary=https://meta-api.com，保留 relay 和 cloudflare 的序列化 ID。新用户默认 primary；旧自动偏好沿用已存线路，成功验证 primary 后优先回归，不要求其延迟更低。健康线路间仍需两轮间隔与冷却，当前不可用时立即选择已验证候选；固定偏好保持不变，不重放模型请求。

复用品牌官网常量和内嵌官网窗口，新网站、控制台链接及充值/Pulse 窗口使用 .com。内嵌会话 Cookie 与 localStorage 初始化限制在新官网域；API 凭据源、已生成工具配置和自动更新分发协议保留原边界。旧 Core 返回两线时禁用新固定选项并提示升级。

活跃笔记审计：[原选路决定](../../implemented/architecture/2026-10-17-client-route-selection.md)部分重叠，本篇替代其两条候选及纯延迟优先规则，其余探测/快照/持久化契约继续复用；[下载择源](../../implemented/architecture/2026-10-17-direct-download-selection.md)相邻，继续独立；其他安装/反馈/账号笔记不被替代。

## Alternatives considered

- 只把新域名加入延迟排名：改动最小，但不能保证用户明确要求的优先新入口。
- 全局替换 API 基址与凭据识别域：可覆盖全部外部直连工具，但引入配置所有权迁移、Cookie 和更新镜像兼容变化；本次复用已有可回退的托管模型选路，仅将官网页面迁到新域。
- 立刻覆盖所有旧偏好：升级即生效，但会丢失用户固定选择且未经当前网络验证；保留旧偏好和已知可用线路，自动模式验证后回归。

## Testing

- Rust 选路 15 项通过，覆盖默认、优先保持/恢复、失败回退、固定模式、旧偏好兼容、请求快照及严格探测。
- 前端 162 文件 1129 项通过，覆盖 .com 固定选择、旧 Core 禁用新选项、官网入口和保存失败。
- 前端类型、格式、renderer 构建、发布版本及笔记检查通过；Rust 格式、Clippy 和另外 4 项 Cookie/官网 origin/凭据边界回归通过。
- 新域名官网、控制台、nonce 身份探测与三个 SSE 事件首次检查成功；后续出现连接/短流超时，旧跳板一轮事件间隔低于 150ms，CF 的 nonce 和流式验证成功（间隔 321/396ms）。这些即时网络结果不能证明长期可用性，也说明需保留失败回退。真实登录充值未执行。
- GitHub 三平台签名构建、完整附件、R2 和平台清单属于发布后核验，不能由本地检查替代。

## Consequences

首选策略可能保留比备选更慢但健康的新线路。探测只代表当前网络且不证明模型推理质量。旧 Core 活跃请求会延后升级；新入口需新 Core。真实账号充值和不同运营商网络不由无凭据探测代替。
