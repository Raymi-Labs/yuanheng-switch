# Agent Note: 元衡桌面端按用户网络选择官方 API 线路

Status: proposed

## Problem

同一 API 服务有跳板和 Cloudflare 橙云两个入口。用户的运营商、代理、网络位置和时段不同，统一固定入口不能持续代表每台电脑的较佳路径。目标是在保持账号、模型、分组和计费一致的前提下，减少连接等待与断流，并让用户能查看及固定所用线路。

本次交付是设计，不包含业务实现、线上测速、DNS 调整或发布。所有阈值为首版候选参数，预览数字为模拟数据；未确认生产线路域名，不能把历史域名直接当作候选。

## Existing capabilities and impact

- [设置页](../../../../src/components/settings/SettingsPage.tsx)已有六个标签；[路由页](../../../../src/components/settings/ProxyTabContent.tsx)含本地代理、供应商故障转移、纠错和出站代理。新增连接线路区域沿用此入口，不增加主导航或第七个标签。
- [工作台体检](../../../../src/components/desktop/YuanhengHealthCard.tsx)提供用户主动检查和修复。连接线路异常可通过现有区域跳到设置，不恢复已移除的常驻状态面板；当前工作树对此组件另有修改，实施时需以合并后的代码为准。
- [端点测速](../../../../src-tauri/src/services/speedtest.rs)使用共享 HTTP 客户端，先热身，再计时一次 GET；[旧表单自动选址](../../../../src/components/providers/forms/EndpointSpeedTest.tsx)只按非空延迟排序，没有验证成功状态和探测正文，不能直接充当自动选路器。
- [本地模型配置](../../../../src-tauri/src/commands/yuanheng.rs)已有独立工具路由；[转发器](../../../../src-tauri/src/proxy/forwarder.rs)已有供应商选择、重试和流式生命周期。线路是同一服务的传输入口，不能通过复制供应商或更换 token 来实现。
- [官方端点约束](../../../../src-tauri/src/yuanheng_endpoints.rs)目前限定主域名及用于迁移的旧域名，并明确禁止带凭据跨源重试。保留逻辑身份与登录域名约束，新增独立、精确的模型传输线路许可，不全局放宽 is_managed_endpoint。
- 复用[连接池与安全诊断](../../implemented/bug-fix/2026-10-12-outbound-connection-stability.md)：同一网络快照继续复用连接，代理变化时换代，已发送的请求正常结束。该笔记部分相关，继续持有连接池与错误脱敏决定，不被本设计取代。
- [更新下载择源](../../implemented/bug-fix/2026-10-12-update-download-failover.md)仅部分相关：可借鉴有界探测；安装包可续传和换源的规则不能移植到计费生成请求。其他已检索的安装、诊断和 R2 笔记不持有模型线路选择决定。现有 proposed 目录未找到同题所有者，无笔记需要归档。

## Proposal

### 产品入口与展示

设置 → 路由顶部新增“连接线路”卡片，默认展开，现有高级项保持原结构。模式用三项单选：自动推荐（默认）、固定跳板线路、固定 CF 线路。每次切换经后端保存成功后展示已应用；失败回滚选择，保留原生效策略。

卡片包含当前实际线路、可用性、最近检测时间、两条线路的响应中位数/检测成功次数和“重新检测”。延迟标为“接口响应”，避免暗示模型首字时间；展示检测次数而不是用三次样本声称长期可用率。不显示虚构综合分数，不要求填写 URL。详情折叠展示域名、检测时间、切换原因和生效范围。

顶部模式控制与当前状态分开：固定线路失败时仍显示固定选择，同时明确“当前不可用”。首次未测显示“待检测”，重测保留旧结果并标注“上次结果”；停止/取消检测不清空原选择。检测过期显示时间与“待复测”，不可继续以绿色实时健康状态展示。

工作台正常时不增加卡片；出现持续连接异常时，在既有连接检查区域显示一行“连接线路异常 · 查看线路”。只在用户打开设置或异常出现时订阅/展示详情，前端是否挂载不决定 Core 是否运行选路器。

### 首版范围与身份

一套官方服务配置包含逻辑服务 ID 和两条经过确认的 HTTPS origin，分别标记 relay / cloudflare。具体生产域名、TLS 证书、上游身份一致性和探测路由是接入前的必备信息。本设计不把 meta-api.vip 当前 DNS 路径或任何旧 cn/otd 域名认定为固定类型。

首版由发布包携带已核对的精确白名单，管理员维护，不开放用户任意增删域名。禁止用户信息、非 443 端口、额外查询参数、片段和跨源重定向；正常验证 TLS。未来远程下发应采用带版本和签名的清单，但不作为首版依赖，主域名不可达时仍能加载本地候选。

登录、Cookie、OAuth、充值、控制台、下载继续使用各自既有入口。仅元衡托管、经过本地 Core 的模型 API 请求参与选路，官方账号模式、自定义供应商和绕过 Core 的外部工具不参与。模型请求只向明确授权的入口发送对应 API token，不把网页登录 Cookie、管理 token 转发给候选。切换不修改逻辑服务身份、provider ID、用户、模型、分组或费用归属。

请求构建时从独立线路解析器取得 origin，保持 API 路径、协议、认证和原路由上下文；每个请求捕获不可变线路快照，后续重试也不重新选线路。共享 reqwest、原始头 Hyper、图片和 WebSocket 等转发路径必须逐一盘点；仅完成协议回归的路径标为已支持，未覆盖路径保持原地址并明确显示范围，不声称所有工具已接入。

### 不计费的探测契约

服务端新增专用探测端点（候选路径 `/api/route-probe`），两条入口转发到同一应用服务。返回固定版本、服务 ID 和原样回传的随机 nonce；设置 no-store 并在 CF 规则中明确绕过缓存。客户端同时核对 HTTP 成功状态、预期类型、服务 ID、nonce 和完整有界正文。静态 Nginx 200、缓存页面、登录页、挑战页和快速 5xx 不算成功；公共探测不返回内部 IP、账号或密钥。

该端点不调用模型、不写消费订单，只证明入口到应用服务可达。服务端限流，客户端限制并发、正文长度和超时；不把限流或维护误报为某运营商线路问题。

每轮每条线路串行执行一次热身及三次计时请求，两条线路最多并行 2 个请求，单次超时候选值 3 秒、整轮 15 秒。分开记录冷启动结果、成功次数、完整响应时间中位数和离散程度；冷启动失败不能被热身后的速度覆盖。若仅一条成功，优先可用；两条成功时先比较稳定性，再比较延迟。

同一服务可增加无模型的短流式探测：发送带序号的固定三段事件并完整结束，最长 4 秒，用于检查缓冲和断流。仅手动检查或怀疑流式问题时启用。真实请求的首字时间、流中断和完成状态提供辅助证据；跨模型/分组不直接比较首字时间，不主动发起计费测速。

### 调度、稳定性与异常

由 Core 持有状态机，UI 通过 IPC 读写。启动使用上次选择作为临时首选并标记待复测；没有记录时沿用既有主入口，后台确认候选后再切换。旧评分超过 15 分钟只作历史展示，不作新网络中的胜出依据。网络/代理代次变化时取消旧探测、作废旧评分、重新检测，旧 IPC 或探测晚到不得覆盖新代次。

触发时机：Core 启动、已支持的平台网络变化事件、系统/应用代理快照变化、用户手动检测、连续连接错误。活跃使用时每 10 分钟附加约 20% 随机抖动执行一轮；离线、休眠和长时间无请求时暂停定时检测，恢复时重测。默认不持久化 SSID、公共 IP 或运营商画像；无法可靠感知的 VPN 内部切换由手动检测及真实连接失败补足。

速度优化切换的初始候选门槛：另一条连续两轮完整成功，且中位数同时改善至少 25% 和 100 ms，当前线路已使用至少 5 分钟。连续两轮需独立采样，手动测速不会绕过稳定门槛。健康线路之间不为轻微抖动切换；该阈值应由不同网络的验收数据调整。

自动模式下，当前线路出现 2 次连续传输失败即触发有界复测；确认另一条可用后，可越过速度切换冷却期，让后续新请求使用另一条。正在进行的请求不迁移，不因为尚未收到首字就并行发到另一条。发送结果不明或已产生流式内容时不自动跨线重放；不对用户生成请求做竞速。现有 provider 重试与新策略组合必须专门回归，避免叠加重试次数。

401、额度不足、模型/分组权限、内容错误不计为网络故障。403 需区分平台权限错误与可辨认的入口挑战；无法分类时显示“请求失败，原因待确认”。应用 5xx、429、维护或模型上游故障不能仅凭状态码归因到线路，应结合专用探测判断。两条都失败显示“暂时无法确认可用线路”，保留偏好、不无限切换，退避复测，不把过去的选择显示为当前健康。

固定模式始终尊重选择，失败也不暗中切换。UI 可提示另一条可用并提供“改用自动推荐”，由用户操作。重新检测只更新结果，不改变固定模式。

### 数据与接口草案

- 持久化仅包含策略版本、逻辑服务 ID、mode（auto / fixed）、fixedRouteId、lastSelectedRouteId、最近切换时间；凭据沿用既有安全存储，不能复制进线路配置。运行期质量、网络代次和探测任务由 Core 管理。
- 拟新增 `get_yuanheng_route_status`、`set_yuanheng_route_policy`、`probe_yuanheng_routes` 和 `cancel_yuanheng_route_probe`，取消按 operation ID 定位，只取消本轮探测。状态变更发布 `yuanheng-route-status-changed`。
- 状态包括 revision、networkGeneration、operationId、mode、selectedRouteId、status（unknown / checking / healthy / degraded / unavailable / inactive）、lastCheckedAt、每线路 samples/latency/errorCategory、切换原因与各工具覆盖范围。
- 重复检测合并到同一任务；模式变更原子落盘再发布新 revision，失败保留旧策略。多个窗口使用 revision 防止旧写覆盖新写，离开页面不取消 Core 正常工作。停止 Core 时显示未生效，不自动打开本地代理。
- 本地有界日志记录线路 ID、时间、原因和错误分类；不记录 token、正文、原始认证头、完整错误链或网络身份，不新增遥测上传。

### 交付顺序

1. 确认两个入口的真实路径、证书、同一服务/账号/分组身份，部署不计费探测端点并确认缓存绕过。服务端上线需要对应项目的明确执行范围。
2. 完成 Core 路由解析、可信入口限制、探测/状态机及已覆盖协议的转发接入，再接设置卡片。生产候选未就绪前功能保持未启用。
3. 以相同模型和分组在真实用户网络验证，包括电信、联通、移动及代理开启/关闭场景，至少覆盖晚高峰；记录成功率、首字、断流和切换次数。模拟测试不替代三网结论。
4. 验收后作为可发布功能更新版本、中文说明、签名安装包和 GitHub Release；本设计提交不升级应用版本。回滚关闭选路器后，新请求恢复既有主入口，已开始请求继续完成。

## Alternatives considered

- **只用 Cloudflare 橙云负载均衡**：统一入口、无需升级客户端，但所有请求先进入 CF；不能绕过用户到 CF 的坏路径。Dynamic Steering 使用监控节点的 RTT，不是逐用户实测。[代理模式](https://developers.cloudflare.com/load-balancing/understand-basics/proxy-modes/)与[动态调度](https://developers.cloudflare.com/load-balancing/understand-basics/traffic-steering/steering-policies/dynamic-steering/)已在方案调研中核对。
- **DNS-only 统一域名分流**：可覆盖未安装桌面端的客户，是保留的服务端补充；受缓存、解析器与入口证书/Host 配置约束，无法替代当前电脑的实时路径比较。
- **复用旧弹窗的一次最低延迟选择**：改动少，但缺少成功响应验证、稳定窗口、持续观测与工具生效范围，容易选中快速错误页。
- **自动改写每个外部工具的 URL**：能覆盖不经 Core 的工具，但增加配置覆盖、重启与回滚风险；首版限定本地托管链路，外部直连工具明确显示不适用。
- **每个生成请求并行竞速**：可能降低尾延迟，但会造成重复推理/计费和流式状态冲突，拒绝采用；只对不计费探测并发。
- **第一版直接上线远程动态清单**：运维更新快，但增加签名、回滚和启动依赖；先使用两条明确授权的内置入口，再独立设计清单更新。

## Acceptance criteria

- 前端在真实应用壳覆盖正常、首次未测、检测中保留旧值、过期、单线失败、全失败、固定失败、保存失败、Core 停止、未覆盖工具和旧结果晚到；窄窗口、暗色、键盘焦点和既有五语言入口通过验收。
- 单元/本地 HTTP 故障测试证明：快速 403/500、错误服务 ID、nonce 不匹配、缓存响应、重定向及 TLS 失败均不能成为有效推荐；记录冷启动失败与流式缓冲/中断。
- 验证多轮稳定门槛、冷却、固定模式、探测合并/取消、离线退避、网络/策略换代、原子保存及重启恢复，不增加无限任务或连接池抖动。
- 请求路由测试覆盖各受支持协议和认证方式：token 仅到白名单，登录 Cookie 不外发，provider/模型/分组保持一致；进行中 SSE 正常结束，发送结果不明时没有跨线重放和重复扣费请求。
- 生产探测确实经过对应入口到应用、无模型调用/费用、无缓存命中；以真实三网和代理场景判断效果，不能用单台开发机验收替代。
- 实施时运行仓库笔记校验、相关 Rust 和前端测试、类型检查、renderer/Core 构建及既有发布检查；发布与生产上线分别核实。

## Risks

最主要的开放输入是两条入口的准确域名和实际转发链路，尚未做本轮生产核对。两条线路共享同一上游时，切线无法修复模型端拥堵或服务整体故障；轻量探测也不保证某个模型请求成功。主域名上的登录与控制台仍是独立可用性边界。

网络事件跨平台可靠性不同，必须给不支持的路径明确状态；后台检测有流量和服务端压力，需按活跃使用、抖动和限流控制。速度阈值为待校准值，不承诺每时每刻最快。新增官方 API 传输 origin 是有意扩展信任边界，必须通过精确白名单、认证分类和真实端到端验证，不能沿用任意端点表单输入。
